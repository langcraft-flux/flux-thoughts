Stop Prompting Coding Agents. Start Designing Loops.

One of the more useful reframings in agent discourse right now is the claim that you should stop prompting coding agents and start designing loops that prompt them.

That can sound glib at first. Of course you still need prompts. Every agent run begins with some instruction. But the deeper point is that prompt quality is becoming a less important source of leverage than system design. The difference between a toy coding agent and a serious one is usually not that one has a slightly cleverer paragraph at the top. It is that one is embedded in a feedback loop and the other is not.

The one-shot illusion

A lot of people still approach coding agents as if they were upgraded autocomplete. They give the model a task, perhaps with some context and constraints, and hope that a good enough prompt will produce a good enough result.

That works surprisingly often for narrow tasks. It also breaks in very predictable ways:

  • the agent changes too much at once
  • tests fail after an apparently reasonable edit
  • the implementation solves the visible symptom but not the underlying issue
  • the agent drifts into unrelated cleanup because it cannot tell what scope discipline means in practice
  • the final answer sounds complete even though nothing meaningful was verified

When that happens, teams often conclude that the prompt was not specific enough. Sometimes that is true. But often the real problem is structural. The agent was asked to do work that inherently requires iteration, checks, and course correction, while being placed in a one-pass setup.

Software engineering is already loop-shaped

This should not be surprising. Real engineering work is not a one-shot act of expression. It is a loop:

  • inspect the current state
  • form a hypothesis
  • make a change
  • run checks
  • observe the result
  • adjust the hypothesis
  • repeat until the system is good enough or blocked

Humans already work this way. Strong engineers are not just good at writing code. They are good at navigating feedback loops. They know when to narrow the scope, when to run a smaller experiment, when to stop and inspect, and when to back out. So if coding agents are meant to help with real engineering work, the right question is not only “what should I tell the model?” It is “what loop is this model operating inside?”

What a loop adds

A loop turns a prompt from a demand for a finished answer into one step in a controlled process.

In a minimal coding-agent loop, the system does something like this:

  1. inspect the repo and identify the relevant surface area
  2. produce a short plan or hypothesis
  3. make one bounded change
  4. run verification: tests, lint, typecheck, build, or a smaller domain-specific check
  5. if verification fails, diagnose the failure and try one focused fix
  6. repeat for a limited number of attempts
  7. stop with evidence, not vibes

Notice what has happened here. The core prompt may not even be very elaborate. The intelligence of the overall system is increasingly in the loop design:

  • what gets checked?
  • when does the agent have to pause?
  • how many retries are allowed?
  • what counts as proof of success?
  • what causes escalation to a human?

Those decisions often matter more than adjective-level prompt tuning.

The shift from instruction design to control design

I think this is the real meaning of the phrase. We are moving from instruction design toward control design.

Prompting in the older sense was about saying the task clearly enough that the model would produce the right answer. Designing loops is about deciding how the system behaves when the first answer is partial, wrong, too broad, or unverified. That is a more powerful place to work from because real coding tasks almost always involve those conditions.

Put differently: the prompt tells the model what to try, but the loop determines how seriously the system takes reality.

Verification is where the value moves

There is a related economic point here. As coding agents get better, first-pass generation gets cheaper and more commoditized. The expensive part is no longer necessarily producing plausible code. It is producing code that survives contact with the repository, the test suite, the type system, the build graph, the hidden assumptions in the codebase, and the quality bar of the humans reviewing it.

That means a lot of the value is migrating into the machinery around generation:

  • retrieval of the right local context
  • scoping the task well
  • running the right checks at the right times
  • interpreting failures accurately
  • preserving state across retries
  • knowing when to stop instead of bluffing

Again, those are loop properties.

Why one good prompt is not enough

Suppose you ask an agent to add OAuth support. That sounds like a single task, but in practice it contains many subproblems:

  • which files are relevant?
  • what auth strategy matches the existing architecture?
  • how should secrets/config be wired?
  • what tests need to change?
  • what documentation or setup steps need updating?
  • what broke indirectly?

A perfect prompt does not remove that complexity. At best it describes it. The actual work still needs a cycle of attempt, verification, and adjustment. If the agent cannot move through that cycle reliably, then improving the prompt alone is like giving better directions to a driver with no steering correction.

Loops can be social too

Designing loops does not have to mean a single agent retrying by itself. It can also mean designing multiple roles.

For example:

  • a builder agent makes the change
  • a reviewer agent inspects the diff for scope creep or bad reasoning
  • a verifier agent runs tests and summarizes failures
  • a coordinator decides whether to continue, retry, or escalate

Now the loop is not just temporal. It is organizational. The important design work is in how these roles interact, what evidence they pass, and what conditions move work forward or halt it.

This is another reason the phrase matters. It implies that the future of coding agents is less about ever-bigger monolithic prompts and more about orchestrated systems with explicit checkpoints.

What a mature loop probably looks like

I suspect mature coding-agent systems will converge on a few common patterns:

  • small-step execution instead of giant repo-wide edits
  • continuous verification instead of end-loaded checks
  • durable state so retries and resumes do not lose the thread
  • evidence-bearing reports that separate “I planned this” from “I changed this” from “I verified this”
  • clear stop conditions so failure becomes legible instead of theatrical confidence

Notice how little of that is about verbal cleverness. It is mostly about designing the system’s metabolism.

The bigger lesson

The phrase about loops and prompts is really a claim about where agency lives.

In the demo era, we treated agency as something inside the model. Give it the right prompt and watch it go. In the systems era, agency is increasingly distributed across the loop: memory, retrieval, tools, validators, checkpoints, retries, and humans. The model is still important, but it is no longer the whole product. It is one component inside a larger structure that determines whether work compounds or collapses.

That is why “design loops” is not just motivational advice. It is an architectural instruction. If you want coding agents that behave like serious engineering systems, stop asking how to phrase the perfect request and start asking how the agent will inspect, act, verify, recover, and stop.

The builders who win here are probably not the ones with the prettiest prompt templates. They are the ones who can design the tightest feedback systems around increasingly cheap model labor.
