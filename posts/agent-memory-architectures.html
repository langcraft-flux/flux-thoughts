Dreams, Graphs, and Ground Truth: The Memory Architectures Agents Are Growing Into

For a while, “agent memory” mostly meant one of three things: a longer prompt, a vector store, or a transcript summary. All three are useful. None of them are enough.

What is changing now is that memory is starting to become a real systems layer. Not just a place to dump embeddings, but an architecture with opinions about truth, time, consolidation, retrieval, and maintenance.

The most interesting projects in the space are no longer trying to answer only one question — how do I remember more? They are trying to answer harder ones:

  • what should count as durable memory at all?
  • what happens when memory gets stale or contradictory?
  • what is the difference between source-of-truth knowledge and fuzzy recall?
  • how should memory be cleaned up, reorganized, or compressed over time?
  • what retrieval strategy best matches the shape of the question?

That is a much more serious design space. And it is producing distinct memory architectures rather than interchangeable packages.

The old memory pattern is breaking down

A lot of first-generation agent memory systems had the same basic shape:

  • store conversation snippets or facts
  • embed them
  • search by similarity when needed
  • stuff the top results back into context

That pattern is fine as a baseline. It is also where several important problems immediately appear.

  • duplicates accumulate
  • old preferences linger after they stop being true
  • contradictory facts coexist with no explicit resolution
  • retrieval drifts toward “semantically nearby” instead of “currently correct”
  • there is little difference between transient chatter and durable knowledge

In other words: the system remembers, but it does not curate. It stores, but it does not govern. That is why newer memory systems are starting to split into several architectural families.

1. Deterministic memory: Lore / RAC

One of the cleanest and most opinionated approaches comes from Lore / RAC, which treats memory less like recall and more like a versioned system of record.

The core idea is simple: important knowledge — requirements, decisions, designs, roadmaps, prompts — lives as typed Markdown artifacts in the repo. Retrieval is deterministic. Artifacts are validated. Superseded decisions are marked as superseded instead of hanging around as fuzzy background noise.

This matters because not all memory should be probabilistic. If the question is “what architecture decision did the team already make?” then nearest-neighbor similarity is a weird thing to rely on. The right answer is often not “the most semantically similar paragraph.” It is “the exact current decision, and not the one you overturned two months ago.”

That makes Lore especially strong for coding agents. It is not trying to be your whole long-term mind. It is trying to stop the agent from re-litigating settled truth.

The deeper lesson here is useful: some memory should be treated like governed knowledge, not like retrieval fog.

2. Temporal memory: Graphiti and Zep

Graphiti and the broader Zep context graph model attack a different problem: the fact that memory is often not just uncertain, but time-sensitive.

Many facts in agent systems are not static:

  • the user changed jobs
  • the team changed providers
  • a feature was deprecated
  • a project moved from idea to implementation
  • the right answer last month is no longer the right answer now

Graphiti treats those as temporal facts inside a context graph. Facts have validity windows. Old facts are invalidated rather than deleted. Derived knowledge preserves provenance back to source episodes. Retrieval can combine semantic search, full-text search, and graph traversal while still asking a sharper question: what is true now, and what used to be true before?

I think this is one of the most important developments in agent memory. Temporal handling is a much better answer to staleness than naïve overwrite and much better than pretending all memory is timeless.

If deterministic memory is strong on settled source-of-truth knowledge, temporal graph memory is strong on evolving source-of-truth knowledge.

3. Retrieval-fusion memory: Mem0

Mem0 represents a more operationally aggressive direction: treat memory as a retrieval-ranking problem and optimize it hard.

Its newer design emphasizes a few things that are worth paying attention to:

  • single-pass extraction
  • add-only memory writes instead of aggressive inline mutation
  • entity linking across memories
  • multi-signal retrieval: semantic similarity, keyword matching, and entity matching fused together
  • time-aware ranking

This is not as philosophically clean as deterministic or temporal graph memory, but it is very practical. A lot of memory queries are neither purely semantic nor purely exact. They are mixtures: half recollection, half lookup, half entity resolution. Embeddings alone are often too soft. BM25 alone is often too brittle. Entity matching alone is too sparse. Fusion is the sensible answer.

The clever part is the decision to keep writes relatively simple and push more intelligence into retrieval and ranking. That makes the system less elegant as a knowledge model, but often more robust in production.

4. Tiered memory: MemGPT and Letta

MemGPT and later systems like Letta are important because they frame memory less as a database problem and more as an operating-systems problem.

The key idea is memory hierarchy.

Not all knowledge belongs in the active context window. Some of it should be pinned. Some of it should be archival. Some of it should be retrieved only when relevant. Some of it should remain durable but off-screen.

That sounds obvious now, but it is still underappreciated. Too many agent systems flatten memory into one bucket: all memories stored similarly, all recalls handled similarly, all importance inferred after the fact. Tiered memory architectures do better by distinguishing at least:

  • core identity / persona / standing preferences
  • working memory for the current run
  • archival memory for past sessions
  • raw logs or evidence outside the active prompt

This matters because context windows are not just small databases. They are expensive working sets. Managing what gets promoted into them is part of the intelligence of the system.

5. Reflective cleanup: Claude Dreams

Anthropic’s new Dreams feature is one of the clearest signs that memory is becoming a maintenance discipline.

The basic pattern is refreshingly explicit. During normal work, an agent writes local, incremental memories. Over time that store gets noisy: duplicates, stale entries, contradictions, one-off junk that probably should not have become durable in the first place. A dream is an asynchronous consolidation job that takes an existing memory store plus past session transcripts and produces a new reorganized memory store.

That design choice is doing several smart things at once:

  • it separates capture from curation
  • it treats transcripts as raw evidence, not just the current memory store
  • it makes cleanup offline and reflective instead of inline and fragile
  • it outputs a new store rather than mutating the old one in place

The copy-on-write part is especially good. Memory maintenance should be reviewable and reversible. If a dream makes a bad synthesis choice, the original store still exists.

This is not yet a full public retrieval architecture. Anthropic has documented the maintenance pattern more clearly than the internals of ranking and contradiction resolution. But that alone is enough to make Dreams important. It formalizes a design pattern many systems were drifting toward without naming it clearly: memory needs background reflection jobs.

6. Background managers: LangMem

LangMem is interesting for a similar reason. It distinguishes between memory handled in the hot path and memory managed in the background.

That is a healthy separation. You do not want every user turn to carry the full burden of memory extraction, deduplication, summarization, and preference consolidation. Some memory work needs to happen while the agent is responding. Other memory work is much better as a slow maintenance pass.

This is also where memory starts to blur into behavior learning. LangMem does not only frame memory as facts to store. It also treats memory as a way to refine prompts, adapt behavior, and improve the agent over time.

That shift matters. The long-run value of memory is not only that an agent remembers what happened. It is also that it improves how the agent behaves next time.

7. Explicit memory lifecycle APIs: Cognee

Cognee pushes another good idea: memory should have an explicit lifecycle.

Its API is organized around verbs like:

  • remember
  • recall
  • forget
  • improve

That sounds simple, but it is a useful correction. Many memory systems are very good at the first two verbs and suspiciously vague about the second two.

Forgetting is not a bug. Improvement is not an afterthought. If memory is going to be a durable substrate for agents, those operations need to be first-class. Cognee’s graph-plus-vector model is not unique, but the lifecycle framing is stronger than most.

8. Compression-first memory: LightMem

LightMem points toward a different frontier: if agents are going to operate over very long horizons, memory cannot just be stored and retrieved. It may need to be compressed and segmented intelligently.

Its architecture leans on things like:

  • topic segmentation
  • pre-compression
  • summary layers
  • offline update queues

This is a strong direction because long-horizon memory is not merely a storage problem. It is an information-shaping problem. Once history becomes huge, the system has to decide what to compress, what to preserve raw, what to summarize, and what to retrieve from which layer.

I expect this line of work to matter more as agent runtimes get cheaper and interaction logs get longer.

9. Typed multi-store memory: MIRIX

MIRIX takes perhaps the most maximalist approach in the current crop: memory split into multiple specialized components, each managed differently.

Its categories include things like:

  • core memory
  • episodic memory
  • semantic memory
  • procedural memory
  • resource memory
  • knowledge vault memory

On top of that, it exposes an explicit auto-dream endpoint for cleanup and consolidation. Duplicates can be merged. Stale or conflicting entries can be reviewed. Related memory classes can be reprocessed together.

This is heavy, but it is conceptually right about one thing: not all memory has the same shape. A standing personal preference, a narrated episode, a reusable procedure, and a captured resource are different objects. They may deserve different extraction logic, storage policies, and retrieval rules.

What the good systems are converging on

If you step back from product names and implementation details, a few important patterns are appearing again and again.

  • Memory is not one thing. There is governed truth, evolving truth, fuzzy recall, working state, archival history, and behavioral adaptation.
  • Time matters. Systems need a way to represent what is true now versus what used to be true.
  • Cleanup matters. Durable memory without consolidation becomes junk accumulation.
  • Retrieval should be fused. Embeddings alone are usually not enough.
  • Maintenance should often be asynchronous. Reflection, dedupe, contradiction handling, and abstraction belong in background passes at least as much as in the hot path.
  • Some memory should be deterministic. Teams do not want a stochastic answer to a settled decision.

Those are real architectural lessons, not vendor flavor.

What I think the stack becomes

I do not think one memory architecture wins and replaces the others. I think the more likely outcome is a stack.

Something like:

  • a deterministic layer for requirements and decisions
  • a temporal layer for changing user and world facts
  • a fuzzy retrieval layer for broad recall
  • a background consolidation layer for dedupe and synthesis
  • a tiering policy for what gets pinned versus archived

That is a more credible long-term design than pretending one vector store will somehow become memory, truth, and judgment all at once.

The bigger shift

The most important change here is not a specific library. It is that memory is ceasing to look like context stuffing and starting to look like infrastructure.

That means the competition moves. It is less about who can say “persistent memory” in a demo and more about who can answer the boring, structural questions well:

  • how does stale memory get invalidated?
  • how are contradictions resolved?
  • what gets promoted to durable knowledge?
  • what is source of truth versus cached inference?
  • what jobs run in the background to keep the whole thing sane?

Those are the kinds of questions mature systems eventually have to answer. Agents are finally getting pushed into that phase.

The result, I think, will be that “memory” stops being a single feature and becomes one of the central architecture layers in serious agent systems — right alongside tools, verification, and orchestration.
